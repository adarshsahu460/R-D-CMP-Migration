KMM shared the brain.
It never shared the face.

Kotlin Multiplatform unified our business logic — networking, models, database, view models. But the UI layer stayed split. Every feature shipped twice.

What it cost us

  • ✕ Every screen implemented twice — once per platform
  • ✕ Same feature, two codebases — a bug fixed on Android had to be re-found and re-fixed in entirely separate iOS code

03 Architecture Overview

One shared core.
Two integration paths.

Both platforms converge on the same commonMain composables + logic. They differ in how they mount it: Android already speaks Compose, so it needs only thin Wrappers. iOS speaks Swift / UIKit, so it needs a bridge — CMPHost → UiController → CMPUI.

Shared Compose UI + Logic (commonMain)
Composable screens · ViewModels · Repositories · Network · DB · Res resources
🤖 Android · already Compose-native
Wrappers
@Destination composable wrappers mount the shared UI directly & wire native callbacks — Google / Microsoft sign-in, Compose Destinations navigation

No bridge needed — Android renders Compose natively.

🍎 iOS · Swift / UIKit bridge
CMPHost
ComposeUIViewController — rendering entry point & lifecycle
UiController
orchestration · state · platform callbacks · iOS keyboard config
CMPUI
renders the shared composable inside the UIViewController
⊕ expect / actual native capabilities both paths share — camera · permissions · file picker · location · analytics · sync
04 The Building Blocks

How the framework actually works.

Real components from the Bizom codebase — not abstractions on a slide.

CMPHost

The platform entry point

On iOS, CMPHost is the bridge — a ComposeUIViewController that hosts the Compose screen and integrates the UIKit lifecycle. On Android, the Activity's own setContent plays this role and screens mount through Wrappers.

MainActivity.ktAndroid

    val navController = rememberNavController()
    BizomTheme {
        DestinationsNavHost(
            navGraph = MainNavGraph,
            navController = navController,
            start = FullScreenControllerDestination(),
        )
    }
}
LoginViewController.ktiOS
fun LoginViewController(
    logger: Logger,
    viewModel: LoginViewModel,
    onAction: (LoginAction) -> Unit
) = ComposeUIViewController {
    LoginScreenUI(viewModel, logger, onAction = onAction)
}
UiController

The traffic controller

Sits between native and CMPUI. Handles navigation, state orchestration, platform callbacks and DI wiring — and configures platform quirks like iOS keyboard focus.

RequirePasswordScreenUIController.ktiOS
fun RequirePasswordScreenUIController(
    viewModel: LoginViewModel,
    userName: String,
    userEnvironment: Int,
    navigateNext: () -> Unit
) = ComposeUIViewController(configure = {
    onFocusBehavior = OnFocusBehavior.FocusableAboveKeyboard  // iOS keyboard quirk
}) {
    RequirePasswordSharedScreen(
        viewModel, userName, userEnvironment, navigateNext
    )
}

If CMPUI is the screen, the UiController is the traffic controller routing native events into it.

05 Migration Strategy

Incremental. Hybrid. Zero big-bang.

We never froze the app for a rewrite. Native and CMP screens coexisted while we migrated feature by feature.

1

Feature-by-feature, not rewrite-everything

Each screen migrated independently. The app stayed shippable the entire time.

2

Hybrid coexistence

Some screens native, some CMP — both live in the same navigation flow. Practical engineering maturity over purity.

3

ComposeUIViewController embedding (iOS)

Each migrated composable wrapped in a UIViewControllerRepresentable and dropped into existing SwiftUI / UIKit navigation — no flow rewrite.

4

Wrappers backfilled as needed

When a migrated screen needed camera/location/share, we added the expect/actual wrapper — keeping UI shared without losing native reach.

Where it bit hardest

The same feature. Two codebases.
One bug, fixed twice.

Plenty of features looked identical on Android and iOS — but ran on entirely separate code. A single bug in shared behavior meant two investigations, two fixes, two reviews. CMP collapsed that.

● Old KMM — fix the same bug twice
  • 1 Bug reported in a feature
  • 2 Reproduce on Android → fix in Android UI code
  • 3 Reproduce again on iOS → fix in separate iOS UI code
  • 4 Two PRs · two reviews · two QA passes
  • ✕ Easy to fix one side and forget the other — platforms drift
● CMP — fix once, both platforms get it
  • 1 Bug reported in a feature
  • 2 Fix once in the shared composable
  • 3 Lands on Android and iOS in the same commit
  • 4 One PR · one review · one QA pass
  • ✓ Platforms cannot diverge — same code, same behavior

Bug-fixing went from 2× the work + drift risk → one fix, guaranteed consistent.

Performance tuning
